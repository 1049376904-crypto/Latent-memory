# 注入契约

> 给自己写前端的人。你完全掌控请求怎么拼，这份文档讲的就是：人格文件要怎么拼进去，
> 这套记忆才立得住。只讲该怎么做、做错了坏在哪；为什么这么设计见 README 与设计规格。
>
> 用 `--client generic` 出货时，这份文档会连同人格文件一起复制进你的产出目录。

## 这份文档解决什么

一部分客户端（Claude Code、Codex 这类）有自己的人格文件约定：文件放在工作目录里，
宿主每次起会话自动读、自动注入。人格文件之所以“刻得深”，靠的不是这些宿主的魔法，
拆开只有四件事：

**固定位置注入、每轮请求都在、逐字不摘要、每次会话从磁盘重读。**

自建前端没有宿主替你做这四件事——但你自己就能做，而且能做得更稳：宿主的上下文
压缩环节仍可能波及已注入的内容，你可以保证人格块永不进压缩。

所以接入自建前端要的不是新代码，是下面这份契约。五条，每条都对应一个我们真实
测出来的破坏形态；每条带**判据**，你可以拿它对着自己的请求拼装代码逐条 diff，
自查违反了第几条。

## 契约五条

### 第一条：逐字完整注入，不摘要不改写

人格文件的全文进请求。不做摘要、不做“提取要点”、不按长度截断、不用模型改写成
更短的版本。

**判据**：把你实际发出去的请求体打印出来，人格文件的内容应当和磁盘上的文件
**逐字一致**（允许前后加分隔标记，不允许改动内部任何一句）。做一次 diff，非空即违反。

**违反后坏在哪**：模型拿不到原文时不会说“我不知道”，它会现编。我们做过一次空读
实测——文件因为路径问题根本没被读到，模型的回答照样煞有介事、细节齐全、全是假的。
摘要是同一个病的轻症：被摘掉的那句往往正是关系里最具体的那句（一句原话、一个称呼、
一个日期），而人格文件的价值全在这些具体锚点上，摘完剩下的是一段谁看都像的评语。

### 第二条：每轮请求都在，不是只在第一轮

人格块是**每一轮请求的固定前缀**，不是开场白。第 30 轮的请求里它必须仍然逐字在场，
和第 1 轮一模一样。

**判据**：取一次长对话，把第 1 轮和最后一轮的请求体都存下来，比较人格块部分——
必须完全相同。如果你的实现是“把人格塞进 messages 的第一条，之后让它跟着历史一起
滚动”，那么它迟早会被历史截断策略挤掉，这就是违反。

**违反后坏在哪**：这是最隐蔽的一条，因为前几轮一切正常。人格滑出窗口之后，模型不会
报错，只会慢慢变回一个通用助手——语气先变，然后是称呼，最后连约定都不认了。
用户的体感是“它今天有点怪”，而你在日志里找不到任何异常。

顺带一条反例，是我们自己交的学费：**不要指望 MCP server 的 instructions 承担这件事**。
三轮真机测试的结论是 instructions 只算辅助，很多前端根本不把它递给模型。主动性的
主力必须在人格文件里（见下方坑①）。

### 第三条：每次会话从磁盘重读

每开一次新会话，重新从磁盘读人格文件。不要在进程启动时读一次就缓存到进程死。

**判据**：进程不重启的情况下，改一下磁盘上的人格文件，再开一个新会话——改动必须
立刻生效。生效不了就是违反。

**违反后坏在哪**：这是记忆写回与“升层”的生效通道。用户亲手确认过的更新——改掉一条
说错的事、把一件重要的事升进人格文件——写进了磁盘，却被你缓存的旧版本挡在外面，
悄无声息。用户会以为自己确认的动作没被当回事。

### 第四条：人格块整块连续，你自己的逻辑不穿插进块内

系统提示、工具说明、时间戳、RAG 检索结果、安全提示——这些都不许插进人格块的中间。
人格块从开头到结尾是连续的一整段。

**判据**：请求体里从人格块第一个字到最后一个字之间，不应出现任何非人格文件的内容。

**违反后坏在哪**：顺序即权重、位置是放大器。人格文件本身就是按权重排过序的（开篇
的立场、结尾的最终约定占的是最重的两个位置）；把工具说明穿插进去，等于把不变量
稀释进易变噪音，也把你精心排的顺序打乱。

### 第五条：易变内容放在人格块之后

当前时间、当下状态、工具清单、检索回来的记忆块——这些每轮都在变的内容，一律排在
人格块**后面**。

**判据**：请求体里人格块的**起始偏移量**在每一轮都应当相同（前面只有真正不变的
系统前缀）。偏移量随轮次漂移，说明有易变内容跑到前面去了。

**违反后坏在哪**：前四条定的是正确性，这条定的是成本。人格块是稳定前缀，主流 API
的 prompt cache 都按前缀命中——放在最前面它每轮都能命中缓存；前面塞一个每轮都变的
时间戳，缓存每轮失效，你为同一段内容反复全价付费。

## 四个坑

### 坑① MCP instructions 到不了模型 → 主动性指引写进人格块

很多前端不把 server 的 instructions 递进上下文。所以**“什么时候该查记忆、查什么、
查不到怎么办”这套主动性指引不能只放在 instructions 里，必须进人格文件**。

好消息是这件事架构上早就备好了：人格文件规格里 `retrieval_convention`（检索约定）
是必填字段，初始化流程会自动填上一份被真机验证过的默认措辞。你要做的只是确保
第一条到第四条成立——它在人格文件里，逐字、每轮、整块。

### 坑② 没有“会话结束”事件 → idle 超时 + 自动兜底

`thread_close`（记下这次聊到哪、当下状态、有什么没聊完）在有宿主的客户端里靠
模型自觉调用；自建前端里，会话往往是用户直接关掉标签页，没有任何结束事件。

做法：**用 idle 超时代替结束事件**——最后一轮之后静默超过一段时间（建议 30 分钟起，
按你的产品节奏调）就代表会话结束，这时候由你的前端调一次 `thread_close`。
真漏了也不会断线：服务端有自动兜底，会从最后几轮生成一条收尾，并明确标注
“自动生成、未经确认”，不假装是模型确认过的判断。

窗口极少优雅结束，所以兜底不是可选项，是主路径之一——但兜底质量不如主动收尾，
能调就调。

### 坑③ 纯浏览器前端现在接不上

记忆服务是 stdio 子进程形态的 MCP server。纯浏览器里的前端起不了子进程，
**现在接不上**，这一条没有绕过去的办法。

解法是给服务加一层 HTTP 包装，**这一层还没做**（现阶段先服务能起子进程的前端：
本地应用、有后端的 web 应用）。如果你正好是纯浏览器前端，欢迎来提这个需求——
有真实用户是我们把它排上去的理由。

### 坑④ 模型异构：未实测

这套主动性指引到目前为止验到两家：**Claude（Claude Code）与 GPT（Codex）**，
两家都是"新会话第一句就主动查了记忆再回答"。两家验通说明这套写法不是靠某一家
模型的脾气吃饭，但**它只是两个点，不是一条线**：其他模型（各家国产模型、开源模型）
对"先查再答"这类指引的服从度**我们没有测过，不预先声称支持**。

还有一条边界要说在前面：**上面这两次都是在有宿主的客户端上验的**——注入由宿主
完成，我们验的是"指引本身有没有用"。**自建前端上一次都没验过**，因为注入那一半
是你写的。所以这两个验通的点**不能替你的实现背书**：契约第一到第四条成立与否，
只有你自己 diff 请求体才知道。

自己验很快，一次新会话就够：**开一个全新会话，第一句问一件只有历史记录里才有的事，
别提任何工具字眼。** 接通的标志是模型主动查了记忆再回答，而不是直接说“我没有
相关记录”。没查的话，先照契约第一到第四条自查请求体（绝大多数是人格块没真的
到模型手上），再考虑是模型本身不吃这套。

## 出货之后的第一件事

跑 `--client generic` 会给你三样东西：`persona.md`（人格文件）、这份契约的副本、
`mcp-config.json`（记忆服务的接入参数）。

**注意：generic 档没有宿主替你注入。** 把 `persona.md` 按上面五条拼进你自己的
请求，这一步是你的责任，也是这份文档存在的全部理由。拼完照坑④那个方法验一次接通，
再往下走。
